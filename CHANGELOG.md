# Changelog

## Unreleased

- Fixed: the e5 and Arctic embedders checked for `cpuAndGPU` only after loading the tokenizer, inside the load timeout, so on a busy machine `make(configuration:timeout:)` could throw a timeout instead of `unsupportedComputeUnits`. The check now runs before any load work.
- Cheaper commits on large stores, with the file format unchanged. A commit no longer copies the whole frame list and encoded frame cache for its rollback (a failed commit truncates them back and restores the frames it changed), no longer sorts every frame's payload range to check for overlaps (it checks its new frames against a sorted index of the committed ones; open still validates the whole TOC), reads the TOC placement floor from that index instead of a pass over every frame, writes the TOC with one `pwritev` instead of copying the cached frames into a new buffer, and stages the text index from the frames at or above its coverage watermark plus inactive ones instead of a copy of every frame. Ingest of 100k MS MARCO passages with precomputed embeddings: 1,024 per `save(contentsOf:)` call went from 108.2 to 97.5 billion instructions (13.4 to 11.6 CPU seconds) and 1,913 to 2,257 docs/s; one `save` per passage from 140.5 to 130.4 billion instructions (19.3 to 17.6 CPU seconds) and 1,489 to 1,619 docs/s (medians of three interleaved runs on a loaded machine). Commits still hash and rewrite the whole TOC, text index and vector segment, which is most of their time.
- Faster vector-only search: the distinctive-token rerank, which can only lift text-lane hits, tokenized every result preview even when the window had none. It now returns at once for such a window. End-to-end vector p50 at 100k MS MARCO passages went from 2.2-2.9 ms to 1.3 ms with the same recall (three interleaved runs); hybrid search is unchanged.
- Faster text indexing: writing a frame to the full-text index first ran a multi-row `DELETE` for the frame's old row even when it had none. SQLite opens a statement savepoint for that, and FTS5 writes its pending terms to disk and merges segments at every savepoint, so each new frame cost an index flush. The old row is now looked up in the mapping table and deleted by rowid only when it exists. Indexing 30k MS MARCO passages in plain SQLite went from 13.9k to 36.4k rows/s with the same index size, and ingest through `Memory.save` at 30k from 8,360 to 11,054 docs/s (median of three interleaved runs).
- Fixed: a commit wrote a TOC of any size, but open rejects one over its limit, so past roughly 120k frames (64 MiB) a commit succeeded and the next open could not read it, falling back to an older footer. Commits now refuse a TOC readers would reject, and the limit is 512 MiB (roughly 950k frames). Builds before this one cannot open a store whose TOC is over 64 MiB.
- Fixed: a commit whose footer reached disk but whose header write failed (or was cut by a crash) left a valid footer that the next open did not see. Its bytes were reused as free space, and a later open that scanned for footers could select it, failing with checksum mismatches. Before a session first reuses freed space it now writes a recovery fence to the header page; a footer at or below the fence counts only if a header page names it, and until the fence is synced the session appends instead of reusing space. Commit generations now advance by 2^32 per writing session.
- New batch save API: `Memory.save(contentsOf:metadata:)` for texts that share metadata and `Memory.save(contentsOf:)` for `(text:metadata:)` documents. Each returns one frame ID per input, in order, the same IDs a loop of `save(_:metadata:)` would return, including the existing ID for a document already stored or repeated earlier in the batch. Runs of new single-chunk documents are embedded with one provider call per `ingestBatchSize` texts and written in WAL-sized batches; empty, multi-chunk and duplicate documents take the `save(_:metadata:)` path in order. Not atomic: if it throws, earlier documents may already be saved. Ingest of MS MARCO passages with precomputed embeddings went from 6,088 to 9,483 docs/s at 20k (1,024 per call), and at 100k from a median of 3,676 to 4,750 docs/s (256 per call) and 5,067 docs/s (1,024 per call) over four interleaved runs on a loaded machine. At 100k most of the remaining time is the commits that WAL pressure forces. That 100k store came out at 660 MB against 395 MB one by one. Its indexes are the same size; the difference is free space left by where commits place their segments, and it can go either way (20k saves with a 1 MiB WAL gave 49 MB batched against 96 MB). `wax-bench perf` takes `--save-batch N` to measure it.
- Smaller stores: a commit's replay snapshot is now written to the header page that commit overwrites, not rewritten in place on the page naming the durable commit. That page is never torn by a later write, so what a commit supersedes (the previous index segments and TOC) is freed as soon as its header is durable instead of one commit later. Space was being held for three generations of index segments: a 100k MS MARCO store goes from 919 MB to 395 MB, and 30k from 325 MB to 197 MB. A header page lost at rest (not by a crash) is no longer covered by the previous commit staying intact; the open footer scan still finds the newest commit when it is near the file end.
- Faster saves: deciding whether a text needs chunking skips encoding a text whose UTF-8 length is within the chunk target, and ASCII text is split for cl100k_base without the ICU regex (same pieces, checked against the regex in tests). Ingest of MS MARCO passages through `Memory.save` went from 7,030 to 9,180 docs/s at 10k and from 4,780 to 5,750 docs/s at 100k (three interleaved runs).
- Cheaper commits on large stores. Staging the text index merged pending frames through a dictionary over every frame (106 ms per commit at 100k frames), deleted the postings of every deleted or superseded frame again on each commit, and the vector segment was copied up to three times while it was serialized. Ingest of 100k MS MARCO passages through `Memory.save` went from 3,767 to 4,318 docs/s (median of three interleaved runs). The file format and search results are unchanged. Commits still rewrite the whole text index, vector segment and table of contents, so their cost still grows with the store.
- New opt-in on-device embedder `BuiltInEmbeddingProvider.e5`: `intfloat/e5-small-v2` (MIT, 384 dimensions) behind the `E5Embeddings` package trait, with masked mean pooling and L2 normalization in the CoreML graph (INT8 weights, FP32 compute, CPU by default). It prepends `"query: "` to search queries and `"passage: "` to stored text, the prefixes the model was trained with. Select it with `config.embedding = .builtIn(.e5)`, or `--embedder e5` in `wax-cli` / `wax-mcp` builds that enable the trait. Its store binding is `Wax` / `E5SmallV2-prefixed`, so a store written with another embedder, or by a pre-release e5 build that embedded without prefixes, refuses to open with it. MiniLM stays the default. The new case is source-breaking for exhaustive `switch` statements over `BuiltInEmbeddingProvider`; add a case or a `default`.
- Fixed: text-index and structured-memory ops queued while another flush was writing were dropped. The frames were never indexed, so they silently missed every text search, and an entity upserted meanwhile could fail with "entity_id lookup failed after upsert". Flushes now settle only the ops they wrote.
- Faster full-text search on large stores: an on-disk text index with 50k or more documents splits each query across up to four read-only connections (never more than half the cores) and merges the results, which are identical to a single query. Hybrid p95 at 100k documents dropped from about 27 ms to about 15 ms. Writes wait for these reads, and later searches wait for a queued write, so a search never mixes snapshots and a commit is not held off by back-to-back searches.
- Behavior change: the Arctic and e5 embedders no longer fall back to the GPU, and refuse `BuiltInEmbeddingComputeUnit.cpuAndGPU` at once with a clear error. Their range input shapes kept the GPU load in MPSGraph shape solving for minutes. A caller that lists `cpuAndGPU` among several compute units moves on to the next one. MiniLM keeps GPU support. Fixed: Core ML model loads no longer hold a process-wide lock, so a slow load under one compute unit no longer blocks loads under another; concurrent loads of the same configuration still share one load.
- New public `VectorSimilarity` (`.cosine`, `.dotProduct`) and `EmbeddingProvider.similarity`, default `.cosine`. A custom embedder for a dot-product-trained model (such as `facebook/contriever`) declares `.dotProduct` with `normalize = false`, and `Memory` then ranks its vectors by raw inner product. Existing providers and stores keep cosine. A store records its similarity in its vector index; opening it with an embedder that declares another one throws a "vector similarity mismatch" `WaxError.io` (a provider that attaches later is reported `unavailable`). A store with a dot-product index can now also be opened before its provider attaches.
- Behavior change: on first open, the text index catches up on frames it had not indexed yet (frames recovered from the WAL after a crash, or written without a text index). The store's owning writer does this (`Memory`, the broker's long-term and live session stores) and commits it on close, so a `Memory` opened only to read can write once on close. Brief opens (corpus, ended-session, migration verification, Markdown export, direct-store CLI) and read-only sessions never write.
- Deprecated `MetalVectorEngine` (package-only, not public API). Wax's search path never used it: vector search runs on `AccelerateVectorEngine` (exact, CPU) or `MetalANNSVectorEngine` (approximate, GPU), which is what to use instead. `MetalVectorEngine` and its Metal shaders will be removed in the next major version.
- MiniLM now uses sentence-transformers mean pooling and reports the embedding identity `MiniLMAll-mean`. Stores written by the old `MiniLMAll` pooler are re-embedded automatically (resumable; text search keeps working meanwhile) and then rebound to `MiniLMAll-mean`. Once a store is rebound, older `wax-cli` / `wax-mcp` builds refuse to open it with a model-binding mismatch. Upgrade every host that shares the store. To re-embed a copy explicitly, run `wax-cli embed-backfill --direct-store --store-path <store> --output <copy>`.
- New public error case `WaxError.vectorsRebuilding(reason:progress:)`, thrown by vector-only search while a store's vectors are re-embedded. This is source-breaking for exhaustive `switch` statements over `WaxError`; add a case or a `default`.
- New public error case `WaxError.vectorIndexStale`, thrown by a commit when an embedding was written after the vector index it carries was staged. It replaces `WaxError.io("vector index is stale relative to pending embeddings; restage vector index before commit")` (the description text is unchanged), so code that matched that `.io` case no longer matches. This is source-breaking for exhaustive `switch` statements over `WaxError`; add a case or a `default`.
- Fixed a race between a concurrent `remember` and `flush`. The flush could fail with a stale-vector-index error, or, if the embedding landed right after the vector sync, commit without that vector so the vector was missing after reopen. Embedding writes now wait while a flush syncs, stages and commits the vector index, so a `remember` that arrives during a flush returns once that commit finishes, and its embedding lands in the next commit. Text-index staging still runs before the wait.
