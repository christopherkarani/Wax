# Changelog

## Unreleased

- Fixed: a vector search racing writes could leave the cached vector engine missing those writes until the next commit. Two searches could refresh the same store's cached engine at once: one applied new pending embeddings to the cached engine while another reloaded and cached a different engine, and the first then recorded its watermark on the reloaded engine, which had never seen those writes. Refreshes of one store's vector engine now run one at a time; searches whose cached engine is current still skip the lock. `concurrentSearchesRacingWritesConverge` failed 10 of 40 runs before and 0 of 60 after, and a new test forces the interleaving.
- Fixed: blocking work and timeout deadlines waited for a free core before they started. `BlockingWork` ran its items (child process waits, pipe reads, synchronous socket round trips) on one shared concurrent queue, and `AsyncTimeout` fired its deadline from a global queue; GCD caps the threads either runs at once by the core count. With every core busy, a 0.1 s CLI call in a parallel test run waited about 50 s to start, which a CI runner pushed past the CLI parity test's 2-minute limit, and a blocked 1 s operation could finish before its 30 ms timeout fired. Each blocking item and each timeout timer now gets its own serial queue, which GCD always gives a thread. In the full parallel suite the CLI parity tests went from 45-56 s to 6-14 s.
- Fixed: a text-index op queued while the index was being staged for a commit could be left out of every later commit. The stage marked the index clean once it finished, so the next stage wrote the op to the in-memory index, saw nothing to stage, and the frame was missing from the committed text index after reopen. Ops queued during a stage now keep the index dirty, and a failed stage leaves it dirty.
- Cheaper commits with a text index: a commit now writes only the pages of the FTS5 database that changed since the previous commit, as a checksummed delta run, instead of the whole database image. Open rebuilds the image from a base and its deltas, applied in order. A commit writes a fresh base instead when the deltas would hold more than a quarter of the image's bytes or number more than 32, and the runs it replaces are freed once its header is durable. An in-memory text engine hands the store SQLite's own buffer, without a copy. Ingest of 100k MS MARCO passages (median of three interleaved runs): with a flush every 1,000 saves, 103.8 to 95.6 G instructions, 15.6 to 13.6 CPU s, store 542.5 to 491.0 MB; with batches of 1,024 and one flush, 66.1 to 62.1 G instructions, 9.0 to 7.7 CPU s, store 563.4 to 494.5 MB. Vector and hybrid p50 and recall are unchanged.
  - File format 3.0. Stores written by earlier builds open and stay on their version until their first commit, which adopts the existing lex blob in place as the base and rewrites both header pages. Builds before this one then refuse the file.
  - `Wax.verify` checks each lex run against the segment catalog, and a deep verify rebuilds the image from the runs. Recovery that finds a footer only by scanning counts it only when the lex runs its commit wrote match their checksums.
- New public `Memory.importDocuments(_:)` bulk load. It takes `(text:, metadata:)` pairs and stores what `save(contentsOf:)` stores: the same frames, chunks, vectors and text index entries. It returns the same IDs, including the existing ID for a document already stored or repeated in the batch. It writes payloads straight to the store instead of the WAL, embeds in `ingestBatchSize` batches, and adds everything to the text and vector indexes in one commit. The import is atomic: nothing is visible or durable until it returns. After a throw or a crash the store holds what it held before, and the space the import wrote is reused. It first commits pending saves. While it runs, other saves, deletes, flushes and `close` wait for it. Searches see the store as it was; text and hybrid searches wait while its final commit runs. Until that commit it holds every new frame record and vector in memory, and it throws `capacityExceeded` at the first batch that cannot fit the commit's TOC or text index. Ingest of 100k MS MARCO passages with precomputed embeddings, against 1,024 per `save(contentsOf:)` call with no periodic flush: 66.5 to 46.4 billion instructions, 12.0 to 7.7 CPU seconds, 5,444 to 9,031 docs/s, 1.98 to 1.40 GB peak memory, and a 563 to 308 MB store. Figures are medians of three interleaved runs on a heavily loaded machine. Vector recall@10 (0.9977) is unchanged, and query latency is within run-to-run noise.
- Faster vector search through `Memory.search` on large stores. Every search ran the structured-memory lane, which looked up the query and each of its tokens as an entity alias (about seven SQLite queries per search) even in a store with no entities; it now checks once whether any alias exists, cached until the next structured write. Packing the recall context encoded each snippet twice and hopped to a separate cache actor per lookup; it now encodes once. At 100k MS MARCO passages, vector p50 went from 8.0 to 4.0 ms and p95 from 46 to 25 ms (medians of five interleaved runs on a heavily loaded machine, load average ~320 on 16 cores), recall@10 unchanged at 0.998. MetalANNS graph search was measured and left off: its best setting reached recall@10 0.979 (HNSW, ef 512) and adds about 15 s to opening a 100k store.
- Fixed: removing a vector from the MetalANNS or Accelerate engine moved the last row into the gap one element at a time. Under Swift 6.2 debug builds each element write copied the whole vector array, so one removal from a 60k × 128 store copied about 4 GB, and the CI test that removes 2,500 vectors ran past the 45-minute gate timeout. Rows are now moved and overwritten with a single mutation of the array.
- Fixed: the first fan-out search opened its read-only connections outside the read/write gate, so a flush running at the same time could fail with SQLite "disk I/O error" (6 of 20 runs of the concurrent-writes test). The connections now open inside the gate.
- New opt-in reranking of search candidates, off by default. `Memory.Config.reranking` takes a new public `Memory.RerankingSource`: `.disabled` (the default; results are unchanged), `.builtIn(BuiltInReranker, RerankingOptions)` or `.custom(any RerankingProvider, RerankingOptions)`. The reranker scores the full frame text of the first `RerankingOptions.candidateCount` candidates (default 20, `1...200`; the search fetches that many even when `topK` is smaller) and `RerankingOptions.fusion` orders them: `.reciprocalRank(k: 10)` (the default) or `.rerankerOrder`. Candidates below the window keep their order; scores stay the retrieval scores, and each reranked item gains a `rerank:` explanation. A reranker error, a wrong score count or a non-finite score makes `search` throw. Other new public API: the `RerankingProvider` protocol, `RerankingOptions`, `RerankingFusion`, `BuiltInReranker`, `BuiltInRerankers.make(_:computeUnit:timeoutSeconds:)` and `BuiltInRerankerError`. The built-in `BuiltInReranker.msMarcoMiniLM` is `cross-encoder/ms-marco-MiniLM-L-6-v2` (Apache-2.0) on CoreML behind the new `MiniLMReranker` package trait (22 MB, INT8 weights, FP32 compute, CPU by default), so default builds do not grow. A document is cut into 288-token windows that share 64 tokens (up to 16) and scored as its best window. Its scores are within 0.015 logits of PyTorch fp32 on the reference pairs on every compute unit (0.045 over 305 benchmark windows from Python), and its windows match the Hugging Face tokenizer's except where `BertTokenizer` already differs (0.34% of benchmark texts: Hangul, symbols such as © ® ™ €, emoji). On Wax hybrid e5 retrieval (text weight 0.4) it raises LongMemEval-S session R_all@5 from 0.905 to 0.938 at the default 20 candidates (17 questions gained, 3 lost) and LoCoMo R_all@5 from 0.555 to 0.609 at 50 candidates (102 gained, 19 lost). On CPU it adds 297 ms p50 per LongMemEval query (about 39 windows) and 89 ms per LoCoMo query (50 windows), predicting in batches of 8 windows.
- Fixed: the e5 and Arctic embedders checked for `cpuAndGPU` only after loading the tokenizer, inside the load timeout, so on a busy machine `make(configuration:timeout:)` could throw a timeout instead of `unsupportedComputeUnits`. The check now runs before any load work.
- Cheaper commits with vectors: a commit now writes only the vectors changed since the previous commit, as a run (rows plus removals) in free space, instead of rewriting the whole vector segment. Readers apply the runs in order. A commit merges at most once: every run when more than a fifth of the rows are dead, otherwise eight runs of the same level into one run a level up, and the rows it adds go straight into the merged run. Merged-away runs are freed only after the merging commit's header is durable, and a footer that only a recovery scan finds counts only when the runs its commit wrote match their checksums. Ingest of 100k MS MARCO passages with precomputed embeddings: one `save` per passage went from 127.4 to 111.6 billion instructions (25.1 to 20.7 CPU seconds), 4,426 to 5,844 docs/s, and 533 to 495 MB; 1,024 per `save(contentsOf:)` call from 97.4 to 80.8 billion instructions (16.8 to 12.2 CPU seconds), 5,669 to 9,075 docs/s, and 739 to 563 MB (medians of three interleaved runs on a loaded machine). Vector query p50 (2.2-2.5 ms) and recall@10 (0.999) are unchanged. Behavior changes:
  - File format 2.0. Stores written by earlier builds open and stay 1.0 on disk until their first commit, which adopts the existing vector segment in place as the first run and rewrites both header pages. Builds before this one then refuse the file.
  - Released builds (waxmcp 0.1.50 and earlier) never removed the catalog entry of a replaced vector segment, so a store with two or more vector commits holds one entry per commit. Such a store opens with only its newest segment adopted, and its first commit drops the other entries and frees their space once its header is durable.
  - Removing a vector (`WaxSession.removeVector`, vector search session `remove`) is now written to the WAL and is durable at the next commit. Before, a removal only lasted until the next vector index was staged. On a 1.0 store the first removal rewrites both header pages first, because 1.0 builds cannot read the new WAL record. Removing the vector of a frame that has none, committed or pending, writes nothing. Photo and video stores remove every retired frame's vector at each index rebuild (open, ingest, delete), so they no longer append a WAL record per retired frame each time, and opening a 1.0 photo or video store no longer upgrades it.
  - A commit writes every pending embedding, so it can no longer be stale. `WaxError.vectorIndexStale`, added earlier in this release, is removed. `vectorIndexNotStaged` is now thrown only when a commit has embeddings for a store that has no vectors yet and no declared dimension and similarity. WAL pressure commits on the same terms: it no longer refuses, failing the write, when every pending embedding on such a store was removed again.
  - After a reload, vector scores can differ from an engine that never closed in the last float bit (rows load in a different order and batched dot products round by position). Top-k results are the same, checked at 60k vectors for cosine and dot, through the sign-code shortlist.
  - Non-finite vectors already in a store are dropped each time it loads instead of being rewritten out of the file.
- Cheaper commits on large stores, with the file format unchanged. A commit no longer copies the whole frame list and encoded frame cache for its rollback (a failed commit truncates them back and restores the frames it changed), no longer sorts every frame's payload range to check for overlaps (it checks its new frames against a sorted index of the committed ones; open still validates the whole TOC), reads the TOC placement floor from that index instead of a pass over every frame, writes the TOC with one `pwritev` instead of copying the cached frames into a new buffer, and stages the text index from the frames at or above its coverage watermark plus inactive ones instead of a copy of every frame. Ingest of 100k MS MARCO passages with precomputed embeddings: 1,024 per `save(contentsOf:)` call went from 108.2 to 97.5 billion instructions (13.4 to 11.6 CPU seconds) and 1,913 to 2,257 docs/s; one `save` per passage from 140.5 to 130.4 billion instructions (19.3 to 17.6 CPU seconds) and 1,489 to 1,619 docs/s (medians of three interleaved runs on a loaded machine). Commits still hash and rewrite the whole TOC, text index and vector segment, which is most of their time.
- Faster vector-only search: the distinctive-token rerank, which can only lift text-lane hits, tokenized every result preview even when the window had none. It now returns at once for such a window. End-to-end vector p50 at 100k MS MARCO passages went from 2.2-2.9 ms to 1.3 ms with the same recall (three interleaved runs); hybrid search is unchanged.
- Faster text indexing: writing a frame to the full-text index first ran a multi-row `DELETE` for the frame's old row even when it had none. SQLite opens a statement savepoint for that, and FTS5 writes its pending terms to disk and merges segments at every savepoint, so each new frame cost an index flush. The old row is now looked up in the mapping table and deleted by rowid only when it exists. Indexing 30k MS MARCO passages in plain SQLite went from 13.9k to 36.4k rows/s with the same index size, and ingest through `Memory.save` at 30k from 8,360 to 11,054 docs/s (median of three interleaved runs).
- Fixed: a commit wrote a TOC of any size, but open rejects one over its limit, so past roughly 120k frames (64 MiB) a commit succeeded and the next open could not read it, falling back to an older footer. Commits now refuse a TOC readers would reject, and the limit is 512 MiB (roughly 950k frames). Builds before this one cannot open a store whose TOC is over 64 MiB.
- Fixed: a commit whose footer reached disk but whose header write failed (or was cut by a crash) left a valid footer that the next open did not see. Its bytes were reused as free space, and a later open that scanned for footers could select it, failing with checksum mismatches. Before a session first reuses freed space it now writes a recovery fence to the header page; a footer at or below the fence counts only if a header page names it, and until the fence is synced the session appends instead of reusing space. Commit generations now advance by 2^32 per writing session.
- New batch save API: `Memory.save(contentsOf:metadata:)` for texts that share metadata and `Memory.save(contentsOf:)` for `(text:metadata:)` documents. Each returns one frame ID per input, in order, the same IDs a loop of `save(_:metadata:)` would return, including the existing ID for a document already stored or repeated earlier in the batch. Runs of new single-chunk documents are embedded with one provider call per `ingestBatchSize` texts and written in WAL-sized batches; empty, multi-chunk and duplicate documents take the `save(_:metadata:)` path in order. Not atomic: if it throws, earlier documents may already be saved. Ingest of MS MARCO passages with precomputed embeddings went from 6,088 to 9,483 docs/s at 20k (1,024 per call), and at 100k from a median of 3,676 to 4,750 docs/s (256 per call) and 5,067 docs/s (1,024 per call) over four interleaved runs on a loaded machine. At 100k most of the remaining time is the commits that WAL pressure forces. That 100k store came out at 660 MB against 395 MB one by one. Its indexes are the same size; the difference is free space left by where commits place their segments, and it can go either way (20k saves with a 1 MiB WAL gave 49 MB batched against 96 MB). `wax-bench perf` takes `--save-batch N` to measure it.
- Smaller stores: a commit's replay snapshot is now written to the header page that commit overwrites, not rewritten in place on the page naming the durable commit. That page is never torn by a later write, so what a commit supersedes (the previous index segments and TOC) is freed as soon as its header is durable instead of one commit later. Space was being held for three generations of index segments: a 100k MS MARCO store goes from 919 MB to 395 MB, and 30k from 325 MB to 197 MB. A header page lost at rest (not by a crash) is no longer covered by the previous commit staying intact; the open footer scan still finds the newest commit when it is near the file end.
- Faster saves: deciding whether a text needs chunking skips encoding a text whose UTF-8 length is within the chunk target, and ASCII text is split for cl100k_base without the ICU regex (same pieces, checked against the regex in tests). Ingest of MS MARCO passages through `Memory.save` went from 7,030 to 9,180 docs/s at 10k and from 4,780 to 5,750 docs/s at 100k (three interleaved runs).
- Cheaper commits on large stores. Staging the text index merged pending frames through a dictionary over every frame (106 ms per commit at 100k frames), deleted the postings of every deleted or superseded frame again on each commit, and the vector segment was copied up to three times while it was serialized. Ingest of 100k MS MARCO passages through `Memory.save` went from 3,767 to 4,318 docs/s (median of three interleaved runs). The file format and search results are unchanged. Commits still rewrite the whole text index, vector segment and table of contents, so their cost still grows with the store.
- New opt-in on-device embedder `BuiltInEmbeddingProvider.e5`: `intfloat/e5-small-v2` (MIT, 384 dimensions) behind the `E5Embeddings` package trait, with masked mean pooling and L2 normalization in the CoreML graph (INT8 weights, FP32 compute, CPU by default). It prepends `"query: "` to search queries and `"passage: "` to stored text, the prefixes the model was trained with. Select it with `config.embedding = .builtIn(.e5)`, or `--embedder e5` in `wax-cli` / `wax-mcp` builds that enable the trait. Its store binding is `Wax` / `E5SmallV2-prefixed`, so a store written with another embedder, or by a pre-release e5 build that embedded without prefixes, refuses to open with it. MiniLM stays the default. The new case is source-breaking for exhaustive `switch` statements over `BuiltInEmbeddingProvider`; add a case or a `default`.
- Fixed: text-index and structured-memory ops queued while another flush was writing were dropped. The frames were never indexed, so they silently missed every text search, and an entity upserted meanwhile could fail with "entity_id lookup failed after upsert". Flushes now settle only the ops they wrote.
- Faster full-text search on large stores: an on-disk text index with 50k or more documents splits each query across up to four read-only connections (never more than half the cores) and merges the results, which are identical to a single query. Hybrid p95 at 100k documents dropped from about 27 ms to about 15 ms. Writes wait for these reads, and later searches wait for a queued write, so a search never mixes snapshots and a commit is not held off by back-to-back searches.
- Behavior change: the Arctic and e5 embedders no longer fall back to the GPU, and refuse `BuiltInEmbeddingComputeUnit.cpuAndGPU` at once with a clear error. Their range input shapes kept the GPU load in MPSGraph shape solving for minutes. A caller that lists `cpuAndGPU` among several compute units moves on to the next one. MiniLM keeps GPU support. Fixed: Core ML model loads no longer hold a process-wide lock, so a slow load under one compute unit no longer blocks loads under another; concurrent loads of the same configuration still share one load.
- New public `VectorSimilarity` (`.cosine`, `.dotProduct`) and `EmbeddingProvider.similarity`, default `.cosine`. A custom embedder for a dot-product-trained model (such as `facebook/contriever`) declares `.dotProduct` with `normalize = false`, and `Memory` then ranks its vectors by raw inner product. Existing providers and stores keep cosine. A store records its similarity in its vector index; opening it with an embedder that declares another one throws a "vector similarity mismatch" `WaxError.io` (a provider that attaches later is reported `unavailable`). A store with a dot-product index can now also be opened before its provider attaches.
- Fixed the broker corpus build leaving each source store open. Its close ran in an unstructured task that could be dropped, for example when the CLI exited; the close is now awaited before the next store is ingested, and a failed close is reported as an error.
- Broker timeouts now use a monotonic clock: the daemon's idle timeout, request-read deadline and shutdown drain, and the client's startup, shutdown, peer-exit grace and response deadlines. A system clock change no longer cuts them short or stretches them.
- Behavior change: on first open, the text index catches up on frames it had not indexed yet (frames recovered from the WAL after a crash, or written without a text index). The store's owning writer does this (`Memory`, the broker's long-term and live session stores) and commits it on close, so a `Memory` opened only to read can write once on close. Brief opens (corpus, ended-session, migration verification, Markdown export, direct-store CLI) and read-only sessions never write.
- Deprecated `MetalVectorEngine` (package-only, not public API). Wax's search path never used it: vector search runs on `AccelerateVectorEngine` (exact, CPU) or `MetalANNSVectorEngine` (approximate, GPU), which is what to use instead. `MetalVectorEngine` and its Metal shaders will be removed in the next major version.
- MiniLM now uses sentence-transformers mean pooling and reports the embedding identity `MiniLMAll-mean`. Stores written by the old `MiniLMAll` pooler are re-embedded automatically (resumable; text search keeps working meanwhile) and then rebound to `MiniLMAll-mean`. Once a store is rebound, older `wax-cli` / `wax-mcp` builds refuse to open it with a model-binding mismatch. Upgrade every host that shares the store. To re-embed a copy explicitly, run `wax-cli embed-backfill --direct-store --store-path <store> --output <copy>`.
- New public error case `WaxError.vectorsRebuilding(reason:progress:)`, thrown by vector-only search while a store's vectors are re-embedded. This is source-breaking for exhaustive `switch` statements over `WaxError`; add a case or a `default`.
- Fixed a race between a concurrent `remember` and `flush`. The flush could fail with a stale-vector-index error, or, if the embedding landed right after the vector sync, commit without that vector so the vector was missing after reopen. Embedding writes now wait while a flush syncs, stages and commits the vector index, so a `remember` that arrives during a flush returns once that commit finishes, and its embedding lands in the next commit. Text-index staging still runs before the wait.
